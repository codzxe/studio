- **No HIGH findings.** The one candidate I chased hardest — rig3d.rs:130-136's stereo-rig expressions comparing `cfg == 2`/`cfg == 3` and `Convergence Of == 2` against 0-based stored enums — is **correct**: `expr/src/host.rs` presents enum values to expressions 1-based (`Value::n(i) => Resp::Num(i + 1.0)`), and the effect's `Configuration` popup stores 0-based (controls.rs:39). Fix wave: don't "correct" those constants.
- **Systemic effectcraft naming (cross-scope, needs a plan, not per-line edits):** every file imports `effectcraft_*` crates (e.g. layer_menu.rs:4-6), and *persisted* identifiers embed the brand: effect ids `"ec.distort.liquify"` (liquify.rs:18), `"ec.control.slider"` (path_nulls.rs:265), `"ec.perspective.3dglasses"` (rig3d.rs:283), `"ec.vr.converter"` (vr_editor.rs:31), plus the `"effectcraftGuides"` file key (view.rs:87). Renaming requires a project-file/effect-id migration (old projects must keep loading); `ec.*` may be acceptable as a frozen namespace — flag for the fix wave to decide.
- **Honest stubs (do not "fix" by deletion without checking the menu tree):** stubs.rs registers zero commands but `menus.rs` historically pointed at stub ids; vpe.rs (`file.importVanishingPoint`) and styles.rs `layer.style.convertToEditable`/`no_psd_styles` are documented always-error menu-parity entries — they do **not** fake success. The dead `not_yet`/`not_yet_run`/`stub!` machinery (S062 entry) is the only removal candidate.
- `render_queue.rs:496` and `mask.rs:598` both clone to work around `&mut`-only helpers; the cheap fix is `&`-taking variants of `path_group`/output-path resolution.
- `markers.set` (markers.rs:224) clones the whole comp (`let snapshot = comp.clone()`) inside the edit closure to read one marker; cheap to avoid but harmless at dialog rate.
- Raw `unwrap()`s in relink*.rs / scripts.rs are all in `#[cfg(test)]` code — not findings.
