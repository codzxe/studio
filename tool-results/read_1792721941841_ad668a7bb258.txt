    20→/**
    21→ * Studio schema (Postgres, drizzle-orm) — PRODUCT_ARCHITECTURE §9.1 (all tables),
    22→ * §9.3 (versions/conflict), §8.8 (credit ledger) + Better Auth 1.7 core/org/api-key/admin
    23→ * plugin tables, verified against `getSchema()` of the installed better-auth.
    24→ *
    25→ * Conventions:
    26→ * - text primary keys (`${prefix}_${uuid}`) generated app-side; timestamps with
    27→ *   time zone (JS Date mode).
    28→ * - Column names are snake_case; TS property names are camelCase.
    29→ *   EXCEPTION: Better Auth tables — property names MUST match the plugin model
    30→ *   field names exactly (the drizzle adapter addresses columns by property name).
    31→ * - Tenant scoping: content tables carry `workspace_id` (or scope through
    32→ *   `project_id` -> projects.workspace_id). Cross-tenant access must read as
    33→ *   "not found" (§12.1) — enforced in `src/repos/*`, not here.
    34→ *
    35→ * Decisions (documented for reviewers):
    36→ * - `project_versions` is NOT unique on (project_id, sha256): re-saving identical
    37→ *   content is a legitimate action and §9.3 forbids rewriting history; the
    38→ *   object store dedupes the blob itself (§9.2 content-addressed). The composite
    39→ *   index exists for fast "is this content already stored" lookups.
    40→ * - `credit_ledger` is append-only by convention; balance is SUM(amount) under a
    41→ *   per-workspace advisory lock (see src/repos/ledger.ts). `amount` and
    42→ *   `balance_after` are int64 (bigint, JS-number mode): D-12 keeps the units as
    43→ *   integer µc, and a Studio monthly grant (10_000_000_000 µc) overflows int32
    44→ *   (max 2_147_483_647) — migration 0003 widened both columns; JS numbers stay
    45→ *   exact up to 2^53, far above any µc balance (M6-A HIGH finding).
    46→ * - `renders`, `comments` and `agent_*` scope through `project_id` per §9.1; the
    47→ *   repos join projects to enforce tenancy.
    48→ * - `projects.current_version_id` and `project_versions.parent_version_id` are
    49→ *   plain text columns WITHOUT FK constraints: they form a circular reference
    50→ *   pair with `project_versions.project_id`, and both are written only inside
    51→ *   repo transactions that hold the project row lock (src/repos/versions.ts),
    52→ *   so integrity is enforced where the conflict rules live (§9.3) without
    53→ *   making schema-level DELETE semantics impossible.
    54→ * - M5 apply/undo (§M5.4/§M5.5): the plan lifecycle (proposed → applied →
    55→ *   undone) lives on `agent_runs` — `applied_at`, `applied_batch_sha256`,
    56→ *   `applied_version_id`, `undone_at`, `undone_by` — because `project_versions`
    57→ *   is IMMUTABLE (§9.3): applying creates ONE version, undoing marks the run
    58→ *   and NEVER deletes or rewrites a version row. Unlike the circular pair
    59→ *   above, `agent_runs.base_version_id` / `applied_version_id` DO carry FKs to
    60→ *   `project_versions.id` (no cycle: `project_versions.agent_run_id` stays a
    61→ *   plain-text back-reference). All three FKs are `ON DELETE SET NULL` so a
    62→ *   cascading project delete never trips over cross-reference ordering
    63→ *   (mirrors `audit_log.actor_id` / `assets.project_id`). Same-project scope is
    64→ *   enforced in repos (a version of another project reads as NOT_FOUND).
    65→ */

   494→// ─────────────────────────────────────────────────────────────────────────────
   495→// Section 7 — Credit ledger (§8.8, §10.2) — append-only
   496→//   grant   +N   purchase / plan allowance / top-up pack
   497→//   adjust  ±N   manual corrections, storage overage, promos (may be negative)
   498→//   reserve −N   hold at run start (pessimistic: balance drops immediately)
   499→//   commit  −M   actual cost at settle time (bounded by the run's hold)
   500→//   refund  +R   release of an unspent hold (full refund on failure/cancel)
   501→// balance = SUM(amount); writers serialize per workspace via pg_advisory_xact_lock.
   502→// ─────────────────────────────────────────────────────────────────────────────
   503→
   504→export type LedgerKind = "grant" | "reserve" | "commit" | "refund" | "adjust";
   505→
   506→export const creditLedger = pgTable(
   507→  "credit_ledger",
   508→  {
   509→    id: text("id")
   510→      .primaryKey()
   511→      .$defaultFn(() => createId("led")),
   512→    workspaceId: text("workspace_id")
   513→      .notNull()

   635→// Section 11 — Billing, user settings, webhook idempotency (§M6)
   636→//
   637→// Decisions (documented for reviewers):
   638→// - One live subscription per workspace: UNIQUE(organization_id) on
   639→//   `subscriptions` — state is UPSERTED on that key (repos/subscriptions.ts),
   640→//   never duplicated per billing cycle; history lives in `invoices`.

   651→//   cents) — a different unit from the credit ledger's integer microcredits

   659→//   BP M6 task 2): UNIQUE(provider, event_id) makes replays and concurrent
   660→//   deliveries resolve to `seen`. It is intentionally NOT tenant-scoped — it
   661→//   stores no tenant content (only provider event ids + payloads for audit).
   662→// - `user_settings` is per-USER (not per-workspace): auto_apply_enabled

   782→// Section 12 — Share links + presence (§M7 tasks 2/5)
   783→//
   784→// Decisions (documented for reviewers):
   785→// - `share_tokens.token_hash` stores sha256(raw token) ONLY: the raw token
   786→//   is returned ONCE in the issue response (route mints it via node:crypto),
   787→//   never persisted — a database leak must not leak usable share URLs.
   788→//   UNIQUE(token_hash) makes lookups index-backed and (theoretically)
   789→//   collision-detecting.
   790→// - `password_hash` is the FINISHED `scrypt$salt$hash` string produced by the
   791→//   GATEWAY route (node:crypto scryptSync): no argon2/bcrypt and NO db-side
   792→//   crypto deps — the repo takes the finished string and only validates its
   793→//   shape.
   794→// - Tenant scoping: share_tokens scope through project_id → projects.workspace_id
   795→//   (repos join projects, §12.1). The public lookup (verifyByHash/getByHash)
   796→//   is deliberately NOT workspace-filtered: the token IS the capability.
   797→// - Revocation/expiry are soft states (revoked_at / expires_at), checked on
   798→//   every public lookup — rows are kept for audit.
   799→// - `presence_heartbeats` is ephemeral state keyed by (project_id, user_id):
   800→//   upserted on every beat, swept by the repo when last_seen_at is older
   801→//   than the TTL (60s default, §M7 task 2). display_name is carried per
   802→//   beat (the UI shows friendly names without a user join); playhead_ticks
   803→//   is bigint mode:"number" like every ticks column.
   804→// ─────────────────────────────────────────────────────────────────────────────
