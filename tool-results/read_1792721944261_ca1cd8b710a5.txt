    20→    20→/**
    21→    21→ * Studio schema (Postgres, drizzle-orm) — PRODUCT_ARCHITECTURE §9.1 (all tables),
    22→    22→ * §9.3 (versions/conflict), §8.8 (credit ledger) + Better Auth 1.7 core/org/api-key/admin
    23→    23→ * plugin tables, verified against `getSchema()` of the installed better-auth.
    24→    24→ *
    25→    25→ * Conventions:
    26→    26→ * - text primary keys (`${prefix}_${uuid}`) generated app-side; timestamps with
    27→    27→ *   time zone (JS Date mode).
    28→    28→ * - Column names are snake_case; TS property names are camelCase.
    29→    29→ *   EXCEPTION: Better Auth tables — property names MUST match the plugin model
    30→    30→ *   field names exactly (the drizzle adapter addresses columns by property name).
    31→    31→ * - Tenant scoping: content tables carry `workspace_id` (or scope through
    32→    32→ *   `project_id` -> projects.workspace_id). Cross-tenant access must read as
    33→    33→ *   "not found" (§12.1) — enforced in `src/repos/*`, not here.
    34→    34→ *
    35→    35→ * Decisions (documented for reviewers):
    36→    36→ * - `project_versions` is NOT unique on (project_id, sha256): re-saving identical
    37→    37→ *   content is a legitimate action and §9.3 forbids rewriting history; the
    38→    38→ *   object store dedupes the blob itself (§9.2 content-addressed). The composite
    39→    39→ *   index exists for fast "is this content already stored" lookups.
    40→    40→ * - `credit_ledger` is append-only by convention; balance is SUM(amount) under a
    41→    41→ *   per-workspace advisory lock (see src/repos/ledger.ts). `amount` and
    42→    42→ *   `balance_after` are int64 (bigint, JS-number mode): D-12 keeps the units as
    43→    43→ *   integer µc, and a Studio monthly grant (10_000_000_000 µc) overflows int32
    44→    44→ *   (max 2_147_483_647) — migration 0003 widened both columns; JS numbers stay
    45→    45→ *   exact up to 2^53, far above any µc balance (M6-A HIGH finding).
    46→    46→ * - `renders`, `comments` and `agent_*` scope through `project_id` per §9.1; the
    47→    47→ *   repos join projects to enforce tenancy.
    48→    48→ * - `projects.current_version_id` and `project_versions.parent_version_id` are
    49→    49→ *   plain text columns WITHOUT FK constraints: they form a circular reference
    50→    50→ *   pair with `project_versions.project_id`, and both are written only inside
    51→    51→ *   repo transactions that hold the project row lock (src/repos/versions.ts),
    52→    52→ *   so integrity is enforced where the conflict rules live (§9.3) without
    53→    53→ *   making schema-level DELETE semantics impossible.
    54→    54→ * - M5 apply/undo (§M5.4/§M5.5): the plan lifecycle (proposed → applied →
    55→    55→ *   undone) lives on `agent_runs` — `applied_at`, `applied_batch_sha256`,
    56→    56→ *   `applied_version_id`, `undone_at`, `undone_by` — because `project_versions`
    57→    57→ *   is IMMUTABLE (§9.3): applying creates ONE version, undoing marks the run
    58→    58→ *   and NEVER deletes or rewrites a version row. Unlike the circular pair
    59→    59→ *   above, `agent_runs.base_version_id` / `applied_version_id` DO carry FKs to
    60→    60→ *   `project_versions.id` (no cycle: `project_versions.agent_run_id` stays a
    61→    61→ *   plain-text back-reference). All three FKs are `ON DELETE SET NULL` so a
    62→    62→ *   cascading project delete never trips over cross-reference ordering
    63→    63→ *   (mirrors `audit_log.actor_id` / `assets.project_id`). Same-project scope is
    64→    64→ *   enforced in repos (a version of another project reads as NOT_FOUND).
    65→    65→ */
