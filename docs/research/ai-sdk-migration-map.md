## 0. Executive summary (what is actually left to swap)

The **transport is already the AI SDK**: `litellm/openai.ts` was rebuilt on `createOpenAICompatible` + `streamText` in an earlier wave (package.json carries `ai@^7.0.153` + `@ai-sdk/openai-compatible@^3.0.78`, lockfile-synced, engines node ≥22, ESM-only). The committed production bundle `apps/web/api/gateway.mjs` (6.87 MB) **already contains both SDK packages**. What remains hand-rolled is the **round loop** in `litellm/runner.ts` (`while (true)` + per-call dispatch + conversation assembly) and the **structured-output plan side-call** (`serverSidePlan`). Round 12 therefore swaps the loop producer, not the transport: build a `ToolLoopAgent` (or multi-step `streamText`) whose tools execute through our existing server seams, and keep emitting the SAME `StudioStreamEvent`s through the SAME `AgentRunStream`.

## 1. Current wire audit (`litellm/openai.ts`)

- **Request shape**: `createOpenAICompatible({ name: "litellm", baseURL: baseUrl + "/v1", apiKey: bearer, fetch, includeUsage: true })` → `provider.chatModel(wireModelOf(deps, request.model))`; `streamText({ model, maxRetries: 0, abortSignal, onError: () => undefined, instructions?, messages, tools?, toolChoice: "auto" })`. System messages become `instructions` (v7 rejects `role:"system"` by default); assistant `tool_calls` + tool results round-trip as `ModelMessage` parts.
- **SSE parsing**: fully SDK-owned (`result.fullStream`); our code only classifies parts. The SDK dispatches complete events at blank lines; a final frame without trailing newline fails the stream.
- **Event vocabulary** (`ModelStreamEvent`, yielded by `streamChatCompletion`): `{type:"text",delta}` | `{type:"tool_call",call:AggregatedToolCall}` | `{type:"usage",usage:{inputTokens,outputTokens}}` | `{type:"finish",reason}`.
- **Tool deltas → `AggregatedToolCall`**: the SDK aggregates streaming fragments per call and emits one `tool-call` part; we re-serialize `part.input` to a JSON string (raw string passed through if the SDK could not parse — the runner's validation repair-turns on it), assign our own monotonic `index`, and normalize the echoed wire name back to the dotted registry id via `toolSeam.originalOf`.
- **Usage parsing**: `finish-step` → `usageOf()` emits usage ONLY when the provider reported numbers (`input>0 || output>0`); absent/zero → NO usage event (the runner falls back to chars/4). `includeUsage: true` on the provider is what makes TH/LiteLLM send the usage chunk.
- **Retries (429 included)**: OUR loop — `RETRY_BACKOFF_MS=[1000,2000]`, `MAX_ATTEMPTS=3`, injectable `sleep` (instant in tests); SDK runs with `maxRetries: 0` because its backoff is real-time. A stream that already emitted any event is NEVER retried (`RetryableStreamError` only when `emitted === false`; otherwise `ModelUnavailableError("The model stream failed mid-response.")`). 429 server_busy (TH account throttle, root-caused round 9) gets no special casing — same 3 attempts then failure.
- **Error classes**: `ModelUnavailableError` (after retry budget / mid-stream death) → runner maps to `RUN_MODEL_UNAVAILABLE` (retryable). `AI_JSONParseError` error parts = non-fatal (malformed SSE frame, keep parsing). `abort` part / `AbortError` → rethrown as `DOMException("AbortError")` → caller maps to `cancelled`.
- **`wireModelOf`**: `deps.modelMap?.[alias] ?? alias` — `LITELLM_MODEL_MAP` env (JSON record) rewrites studio alias → provider model id AT THE WIRE ONLY; every internal seam (entitlements, run rows, §8.8 credit rates via `MODEL_CATALOG`) keeps the alias. Injected through `OpenAIClientDeps.modelMap` ← `LiteLLMRunnerDeps.modelMap` ← `createRunnerForEnv(env.litellm.modelMap)`.
- **`toolSeam`** (load-bearing, live on Token Harbor): registry ids carry dots (`studio.get_context`) but the OpenAI-compatible name grammar is `^[a-zA-Z0-9_-]{1,64}$` — strict validators (TH edge) 400 dotted names. `wireToolName` rewrites dots→underscores for registration; the model's echoed name (either form) normalizes back through the same sanitizer. Prompt + history + all internal seams keep dotted ids.
- **Deps injection**: `baseUrl, bearer (virtualKey ?? apiKey), modelMap?, fetch? (fake SSE server in tests), sleep? (instant backoff in tests)`.

## 2. Runner seam audit (`runner.ts` + `litellm/runner.ts` loop)

- **`AgentRun`**: `runId, threadId, projectId, workspaceId, model (ALIAS), baseVersionId, message, context, pinned, reservedCredits, history?` — history = last-6 user/assistant TEXT turns (§8.3), loaded by the chat route from `agent_messages`.
- **`AgentRunStream`**: `emit(RunStreamPayload)` (RunLog assigns `seq`+`runId`, pins terminal, captures plan), `yieldToStream()`, `expectToolCall(toolCallId, tool)` (the POST /v1/runs/:id/events validator), `waitForToolResult(toolCallId)` → `{ok:true,result}|{ok:false,reason:timeout|aborted}` (30 s, `TOOL_RESULT_TIMEOUT_MS`; timeout → `EDITOR_DISCONNECTED`, abort → `cancelled`), `signal: AbortSignal` (client disconnect or POST cancel).
- **`AgentRunOutcome`**: `completed{committedCredits}` | `failed{code,message,retryable}` | `cancelled`. The chat route finalize: completed → ledger settle + `credits` event + `run.completed` + persist assistant text; failed/cancelled → `refundAll`.
- **The loop** (`createLiteLLMRunner.start`): `run.started` → `while(true)`: abort check; `rounds >= maxSteps` → `RUN_STEP_LIMIT` (non-retryable) BEFORE the call; redacted fingerprint log (chars + sha256[0:16] only); `readModelRound` (tools on, deltas → `message.delta`); push assistant turn (with `tool_calls`); no calls → break (final answer). Per call: `validateToolCall` (unknown tool / JSON / curated Zod args) — invalid ⇒ strike; ≥2 strikes ⇒ `RUN_INVALID_TOOL` (non-retryable); 1st ⇒ repair turn (`{error:"VALIDATION_FAILED",message}` as the tool result). `studio.plan_edit` ⇒ `serverSidePlan` (separate NO-TOOLS round: strict-JSON prompt, `extractJsonObject` fence/brace tolerance, `EDIT_PLAN_SCHEMA`, 2 attempts with the validation error appended) ⇒ `plan` event (compile-enriched: `compiledBatch/resolutionRequests/risk/estimatedCredits`, un-enriched on compile fail) + `tool.result`. Write tools ⇒ propose-only: `writeToolCarrierPlan` → `compilePlanSafe` → `WRITE_TOOL_RESULT_SCHEMA` ⇒ client gets `{proposedBatch, note}`, model gets REDACTED `{proposed, summary, note, stepCount}` (law #5). Read tools ⇒ `expectToolCall` + `tool.started` then `waitForToolResult`. Write-tool rescue: carriers merged (`mergedCarrierPlan`, undo_run excluded) into one plan event when no plan fired. End: `committedCreditsFor` (§8.8: `ceil(in/1000×rateIn + out/1000×rateOut)`, min 1, `MODEL_CATALOG[alias]`; usage unseen ⇒ chars/4 over the conversation, assistant=output).
- **Error → RUN_ mapping** (all sites): abort/AbortError → `cancelled`; `ModelUnavailableError` → `RUN_MODEL_UNAVAILABLE` (502, retryable); unexpected → `INTERNAL` (retryable); `RUN_STEP_LIMIT`, `RUN_INVALID_TOOL` non-retryable; `EDITOR_DISCONNECTED` retryable; route-level: `RUN_CANCELLED` (409), `RUN_NOT_FOUND`/`RUN_NOT_ACTIVE`/`RUN_ALREADY_APPLIED` etc. in `errors.ts` + `routes/`.

## 4. Emitting StudioStreamEvent from the AI SDK (client compat layer)

The client contract lives in `RunLog` (seq, Last-Event-ID replay, terminal pinning, `expectToolCall` map) and the routes — NOT in the model loop. The rebuild keeps `AgentRunner.start(run, stream)` and produces the same `stream.emit()` calls from two producers:

1. **Parts loop** (`for await (const part of result.stream)` — v7 name): `text-delta` → `message.delta`; `abort` → cancelled; `error` → RUN_MODEL_UNAVAILABLE/INTERNAL classification (identical rules to openai.ts 501-519); `finish` → step-count check for RUN_STEP_LIMIT. Do NOT map `tool-input-delta` (we never emitted `tool.delta`).
2. **Tool `execute` closures** (server-resolved tools): plan_edit → compile + `plan` + `tool.result`; write tools → proposal `tool.result`; read tools → `expectToolCall` + `tool.started` then pending promise (the runs route still emits the client's `tool.result` on POST — unchanged). `tool.started` fires at execute start with the SDK-validated input (zod-curated args), preserving "tool.started only for validated calls".
3. **Callbacks**: `onStepStart` → fingerprint log; `onStepEnd` → usage sum; `onAbort` → cancelled bookkeeping; `onEnd` → rescue-merge (carriers collected in execute) + `committedCreditsFor`.

Event order preserved: parts arrive in generation order; executes run during the step (set `toolCallConcurrency: 1` — today's loop is strictly sequential, `tool.started` in call order; SDK default is concurrent); plan/rescue events still land before `run.completed`; finalize (credits + terminal) stays in the chat route. With that, the SSE byte stream is event-for-event identical: **100% client compat is achievable** — `STUDIO_STREAM_EVENT_SCHEMA` needs no change and the editor reducer/POST-seam/Last-Event-ID replay are untouched.

- **If/when tool parts are stored** (round-12+ stores richer rows): reuse the ALREADY-WRITTEN converter `toSdkPrompt()` (openai.ts 262-350) — it maps `OpenAIChatMessage{role:"assistant", tool_calls}` → `{role:"assistant", content:[{type:"tool-call",toolCallId,toolName,input}]}` and `role:"tool"` rows → `{role:"tool", content:[{type:"tool-result",toolCallId,toolName,output:{type:"json"|"text",value}}]}`, resolving `toolName` from the requesting assistant turn, and closing unanswered calls with the `SEPARATE_STEP_TOOL_OUTPUT` stub (only needed for replaying the plan side-call's open call — disappears if plan_edit is execute-resolved in-loop). ## 7. Risks (flagged, with severity)

1. **HIGH — Tool-result wait seam semantics**: `timeout:{toolMs:30_000}` converts a timeout into a `tool-error` part (model may retry) instead of today's terminal `EDITOR_DISCONNECTED` run failure. The runner must distinguish "timed-out read tool" (fail run, retryable) from other tool errors, and pending promises must reject on abort. Also `toolCallConcurrency` MUST be 1 (default is concurrent — would break seq ordering, `expectToolCall` registration order, and the runs-route validator assumptions).
2. **HIGH — Credits/usage parity (§8.8)**: commit math must stay `ceil(in/1000×rateIn + out/1000×rateOut)`, min 1, alias-keyed `MODEL_CATALOG`; per-step usage summed with the >0 filter; the plan side-call's tokens join the same commit; the chars/4 fallback (usage never seen) must survive — its input is today's `OpenAIChatMessage` JSON; if fed `ModelMessage`s the char counts shift slightly (recompute or keep a converted shadow copy). Cancelled/failed runs refund — `onAbort`/outcome mapping must keep that.
3. **HIGH — plan_edit structured output**: `generateObject` would emit `response_format: json_schema` on the wire — UNVERIFIED against Token Harbor free-tier (could 400 and break the live DeepSeek path). The bespoke STRICT-JSON prompt + `extractJsonObject` + 2-attempt loop is proven live. Recommend keeping it as a no-tools `generateText` side-call (or execute-resolved in-loop); only adopt `generateObject` after a live probe of TH's `response_format` support.
4. **MEDIUM — Retry/test seam**: SDK `maxRetries` backoff is real-time (breaks the instant-sleep test seam); mid-stream `streamRetries` (default 0) is fine to leave off. Keeping `maxRetries: 0` + OUR 3-attempt wrapper preserves §8.9 exactly (incl. no-retry-after-emission) — but with the agent owning the loop, "retry the round" must become "restart the whole run-level attempt" or be dropped for pre-first-event failures only. Decide explicitly; 429 TH throttle currently relies on this budget.
5. **MEDIUM — Step-cap outcome**: `stopWhen` ends the generation "successfully" (finishReason `step-count`); we must translate to `failed RUN_STEP_LIMIT` (non-retryable) to keep run rows/UX parity — partial deltas already streamed is unchanged behavior.
6. **MEDIUM — Repair policy parity**: 2-strike `RUN_INVALID_TOOL` is OURS; the SDK's repair/tool-error loop retries within the step cap. Keep the strike counter (count validation failures across steps) and the unknown-tool "available tools" repair message. `NoSuchToolError.isInstance` for the unknown-name case.
7. **MEDIUM — toolSeam survival**: ToolSet keys must be underscore wire names, echoes normalized via `originalOf`, prompt/history keep dotted ids. A regression here 400s every live tool call on TH (the round-10 stale-test incident proved the seam is load-bearing).
8. **LOW — ESM/bundling**: pure-ESM SDK into ESM bundle — already proven in the committed artifact; no new deps, no CJS interop, engines match. Only watch: never import `ai` from `apps/web` client code (bundle is server-only).
9. **LOW — Abort semantics**: SDK calls `onAbort`, NOT `onEnd`, on abort; `consumeStream()`-style draining may be needed to avoid unhandled rejections on `result.text`/`responseMessages` promises (openai.ts already null-attaches the aggregate promise — replicate for agent results).
10. **LOW — History persistence**: assistant text is assembled by finalize from `message.delta` events — unchanged; no new rows needed. `agent_steps` single-writer (finalize walks the RunLog) keeps working because it reads the log, not the loop.

## 8. Verdict

- **Bundling**: feasible with zero new dependencies — esbuild 0.25.12 ESM bundle already ships `ai@7.0.153` + `@ai-sdk/openai-compatible@3.0.78` in production.
- **StudioStreamEvent compat: 100% keepable** — the wire contract is owned by `RunLog` + routes; the AI SDK swap only changes the producer of `emit()` calls. No schema change, no client change, no route change.
- **Biggest rebuild decisions**: (1) read-tool wait → execute + toolMs with explicit EDITOR_DISCONNECTED re-derivation + `toolCallConcurrency: 1`; (2) keep plan_edit's hand-rolled STRICT-JSON side-call (not `generateObject`) until TH `response_format` is probed; (3) keep the maxRetries:0 + own-retry posture for §8.9/test-instant backoff.
