5. Editor GPU boot + dist bootstrap patch (2026-10-25). The frozen dist's
   `index.html`/`worker.js` were hand-patched **in lockstep with the canonical
   sources** (`editor/apps/effectcraft-web/web/`) — the two trees were
   byte-identical before and after, so the next `cargo xtask web` regenerates
   the dist from the patched sources unchanged. What changed and why (the
   first live "failed to create wgpu surface … webgl2 not available" report on
   a machine with a discrete GPU):
   - **Discrete GPU, not the iGPU**: every `navigator.gpu.requestAdapter` call
     that names no preference is wrapped to ask for
     `powerPreference: "high-performance"` (hybrid laptops otherwise boot the
     editor on the integrated GPU), and when no WebGPU adapter answers the
     page takes the canvas's WebGL2 context FIRST with wgpu's own
     `antialias: false` plus the same hint (the first `getContext` decides the
     GPU; wgpu reuses the existing context). `editor/…/src/app.rs` now also
     passes `PowerPreference::HighPerformance` through `eframe::WebOptions` —
     source landed, **dist rebuild pending** (no Rust toolchain on the box
     this session; the JS shim covers the shipped bytes meanwhile).
   - **Fail fast with the remedy**: a GPU pre-flight runs BEFORE the 49 MB
     engine download — no adapter and no WebGL2 means the browser's hardware
     acceleration is off (the usual cause on GPU machines), and the page says
     so immediately instead of failing after the whole boot.
     `effectcraftLoad.gpu` reports `{webgpu, webgl2, renderer, software}`.
   - **Faster open (dev + prod)**: the host page starts the engine's
     fetch + compile the moment the capability gate passes
     (`src/lib/editor-warmup.ts`, published as `window.__studioEditorWasm`);
     the dist's bootstrap adopts the compiled module instead of downloading
     again, so the 49 MB stream overlaps the iframe's own load. The boot
     overlay shows the live download/compile progress.
   - The capability gate now probes `requestAdapter` for real (a browser with
     hardware acceleration off still exposes `navigator.gpu` — presence alone
     let users through into the crash), and the unsupported state names the
     hardware-acceleration remedy. Proven on-box: the m7 reload-persistence
     e2e leg passes (32.1 s) on the patched dist — boot, open, reload intact.
6. Graphics-device-loss recovery (2026-10-25). The live report: mid-session,
   the dist reports "The graphics device was lost … GPU device lost (Unknown):
   A valid external Instance reference no longer exists" on an RTX 3050
   machine — Chrome's GPU process connection died (a lost WebGPU device
   cannot be revived in place; the GPU itself is fine). The embedded
   editor's dead-end dialog ("save the project before you reload") was also
   wrong for the Studio context, where the gateway autosave is the
   persistence authority. What landed:
   - `js/host.js` `showDeviceLost` (patched in lockstep with the dist copy —
     the trees stay byte-identical, `cargo xtask web` reproduces them) now
     tells an embedding same-origin host FIRST —
     `window.parent.postMessage({type: "studio:deviceLost", message}, origin)`
     — and keeps the fallback dialog for the standalone page and unknown
     hosts, unchanged.
   - The web host (`use-editor-session.ts` 7) listens for the report (origin
     + source + type checked) and owns the recovery: the engine is still
     alive on the CPU, so it saves NOW through the real autosave chain
     (label "Save after graphics device loss"), then reloads the page — RSC
     re-fetches the manifest and the editor reopens with the latest version
     on a FRESH device. A save that fails or outruns the 20 s budget parks on
     the `DeviceLostOverlay`'s Try again / Reload now buttons (a late
     success still reloads on its own; the deliberate reload bypasses the
     unsaved-changes guard so recovery never double-prompts). Read-only
     sessions skip straight to the reload (nothing of ours to upload).
   - Upstream `tests/page.mjs` grows the embedded-host arm (the parent is
     told once, the fallback dialog still shows); the web host suite grows
     four recovery arms (save+reload, failed stage + buttons, foreign
     messages ignored, read-only straight reload).
   - **GPU circuit breaker (2026-10-25, later the same day).** The live
     follow-up: on a machine whose WebGPU stack dies at device creation
     ("GPU device lost (Unknown): A valid external Instance reference no
     longer exists" — a Dawn/WebGPU failure; WebGL2 rides ANGLE/D3D11, a
     different driver path), the recovery above LOOPED: every reload booted
     WebGPU again, the fresh device died the same way, the editor never
     opened. A reload cannot fix a persistently broken WebGPU stack. What
     landed:
     - `apps/web/src/lib/editor-gpu-fallback.ts`: the FIRST device loss in a
       tab session arms a sessionStorage marker (`studio:editor-gpu-fallback`;
       a same-origin iframe shares the tab's sessionStorage with the parent).
       While armed, the editor iframe boots
       `/editor/?empty&gpu=webgl2&nogpuworkers`, the app-start prewarm
       prefetches that exact document URL, and a dismissible banner names the
       cost (WebGL2 + CPU-rendering workers — playback may be slower) with a
       "Try WebGPU again" button that disarms and reloads (the right move
       after a GPU-driver update; a new tab starts clean — the marker is per
       tab, never a machine-wide verdict).
     - The dist (both copies in lockstep, `cargo xtask web` reproduces them):
       `index.html`'s pre-flight honors the marker and `?gpu=webgl2` — a
       `requestAdapter` shim answers `null`, which is the PROVEN no-adapter
       path (the WebGL2 context is taken first, egui-wgpu runs its WebGL
       backend), and `history.replaceState` normalizes `nogpuworkers` into
       the URL so the engine's own query flags see it; `host.js`'s
       standalone-dialog Reload arms the same marker before reloading. The
       `effectcraftLoad.gpu` diagnostics carry a `fallback` field.
     - Tests: lib/editor-gpu-fallback (5 arms), editor-host (+4 compatibility
       arms: URL + banner, Try-WebGPU-again disarm+reload, dismiss, plain
       boot without the marker), upstream page.mjs (Reload and Reload Anyway
       arm the marker), e2e m3-device-lost extended — the reopen itself now
       lands ON the compatibility URL with the banner visible.
